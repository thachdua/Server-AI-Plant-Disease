# iOS Code Review and Quality (Plant Disease App)

## Overview

Multi-dimensional code review with strict quality gates tailored for iOS 16 development on resource-constrained devices (like the iPhone 8). Every change gets reviewed before merge — no exceptions. Review covers five axes: correctness, readability, architecture (MVVM), security, and performance.

**The approval standard:** Approve a change when it improves overall code health and strictly adheres to the project's iOS 16 and farm-environment constraints.

## When to Use

- Before accepting any code generated by the Cursor agent.
- After completing a feature implementation (e.g., Scanner, History, Dictionary).
- When refactoring existing Swift code.
- After any bug fix (review both the fix and the regression).

## The Five-Axis Review

Every review evaluates code across these dimensions:

### 1. Correctness (The iOS 16 Gate)

Does the code do what it claims to do, and will it compile on iOS 16?

- **CRITICAL:** Does it use any iOS 17+ exclusive features? (Flag immediately: `@Observable`, `ContentUnavailableView`, `.containerRelativeFrame`, `SwiftData` if used without care).
- Does it match the spec or task requirements?
- Are edge cases handled (e.g., camera permission denied, no internet connection)?
- Are error paths handled with clear, Vietnamese messages suitable for farmers?
- Are optionals unwrapped safely (no force unwrapping `!` unless guaranteed safe)?

### 2. Readability & Simplicity

Can another engineer (or agent) understand this code without the author explaining it?

- Are names descriptive and consistent with Swift API Design Guidelines?
- Is the UI code clean? Are massive SwiftUI `body` properties broken down into smaller, focused sub-views?
- Is the code organized logically (related modifiers grouped)?
- Are there dead code artifacts: no-op variables (`_unused`), or `// removed` comments?
- Is the UI suitable for the target audience (farmers)? (Check for large fonts like `.title3` or `.headline` and clear icons).

### 3. Architecture (Strict MVVM)

Does the change fit the system's design?

- Does it follow the strict MVVM pattern defined in the spec?
- **CRITICAL:** Is business logic (AI inference, network calls, data processing) kept entirely out of the SwiftUI View?
- Are ViewModels properly managing state using `@StateObject` or `ObservableObject`?
- Are module boundaries clean (e.g., `ScannerView` should not directly access `CoreData` contexts; it should use a service)?

### 4. Security

Does the change introduce vulnerabilities?

- Are API keys (if any, for weather or external services) kept out of version control?
- Is user data (location, photos) handled with respect to privacy permissions (`Info.plist`)?
- Are external data sources (FastAPI responses) validated before use?

### 5. Performance (The iPhone 8 Gate)

Does the change respect the strict memory and processing limits of the iPhone 8?

- **CRITICAL:** Are large images (`UIImage` from the camera) downsampled before being processed or displayed to prevent OOM (Out of Memory) crashes? (Memory footprint must stay < 150MB).
- **CRITICAL:** Is CoreML inference or heavy image compression running on a background thread (`Task.detached`)? The Main Thread must never be blocked.
- Are network calls to FastAPI configured with a strict timeout (e.g., 15s) to handle weak farm networks?
- Are long lists (History) optimized (e.g., using `LazyVStack` and Core Data batch fetching)?
- Are unnecessary UI re-renders avoided by keeping `@State` tightly scoped?

## Review Process

### Categorize Findings

Label every comment with its severity:

| Prefix | Meaning | Author Action |
|--------|---------|---------------|
| *(no prefix)* | Required change | Must address before merge |
| **Critical:** | Blocks merge | iOS 17 code used, Main thread blocked, OOM risk from full-size image, broken functionality |
| **Nit:** | Minor, optional | Author may ignore — formatting, style preferences |
| **Optional:** | Suggestion | Worth considering but not required |

## The Review Checklist

```markdown
## Review: [Feature/Component Name]

### 1. Correctness & Compatibility
- [ ] Compiles on iOS 16 target.
- [ ] NO iOS 17+ exclusive APIs used (`@Observable`, `ContentUnavailableView`, etc.).
- [ ] Safe optional unwrapping (No `!`).
- [ ] Edge cases and errors handled gracefully (in Vietnamese).

### 2. Readability & UI/UX
- [ ] SwiftUI Views are small and composable.
- [ ] Typography and icons are large and clear (Farmer-centric design).
- [ ] Variables and functions are clearly named.

### 3. Architecture (MVVM)
- [ ] Zero business/network/AI logic inside SwiftUI Views.
- [ ] Correct use of `@StateObject`, `@ObservedObject`, `@State`, `@Binding`.

### 4. Performance (iPhone 8 Constraints)
- [ ] CoreML / Network tasks execute on background threads.
- [ ] Camera images are aggressively downsampled to prevent memory spikes.
- [ ] Network requests have explicit timeouts.
- [ ] Lists use `LazyVStack` or equivalent optimizations.

### Verdict
- [ ] **Approve** — Ready to merge/accept.
- [ ] **Request changes** — Critical issues must be addressed.
```
